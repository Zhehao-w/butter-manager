## 发现：1 项 P1、3 项 P2

### CR-01 · P1 · 删除确认未绑定目录身份，可能回收后来替换的目录

位置：`src-tauri/src/deletion.rs:15`、`src-tauri/src/commands.rs:827`。

`DeletePlan` 只记录路径、标题、存档路径及阻断信息，没有记录原目录的文件系统身份。确认时重新生成计划并比较 `current != plan`，因此不能识别同一路径下的目录替换。一般游戏删除和库内查重删除共用此流程。

隔离复现：

1. 在临时库注册游戏，生成无阻断的删除预览。
2. 将原游戏目录移到临时目录的另一个位置；在原路径建立含 `unrelated.txt` 的新目录。
3. 使用同一个游戏记录与 token 重新生成预览，新旧计划完全相等。
4. 调用现有 `apply_files`，用临时目录内的重命名模拟回收；操作成功处理了替换目录。

原游戏仍保留于隔离目录，未调用原生回收站。此复现不需要并发竞争，只需用户在确认期间整理文件夹。

建议：服务端预览保存游戏目录和独立存档目标的身份，确认后、实际回收前重新验证；目录被替换时拒绝并要求重新预览。复用 AppData 清理及 Import 已有身份校验方式，不依赖名称、大小或是否有相同的子路径。保留现有共享路径、任务互斥和回收失败处理。

必要回归：游戏目录替换、外部存档目录替换、查重删除复用；断言回收回调未调用、库记录及替换目录均保留。

### CR-02 · P2 · 游戏详情启动绕过全局任务禁用，后端也未补齐

位置：`src/App.tsx:2783`、`src-tauri/src/commands.rs:1194`；对照主页 `src/App.tsx:1035`。

主页启动按钮检查 `taskActive`；详情按钮仅检查局部 busy、launching、关闭确认和路径状态，没有检查传入的全局任务锁。`play_game` 仅检查 `imports.blocks_game`，也不检查 `tasks.active()`。`blocks_game` 排除 pending 项，不能代替全局任务互斥。

隔离组件测试复现：Mock 一个持续运行的扫描任务，返回游戏库，主页启动禁用；打开同一游戏详情，启动按钮仍可点击，并调用 `api.play`。所有 API 均为 Mock，未启动真实程序。后端缺少任务检查通过代码核对确认，未实际执行并发游戏启动。

影响：用户通过详情可以绕过主页的“当前任务完成后可启动”规则。涉及导入准备或其他任务的执行窗口时，启动与文件任务之间的保护不一致；不代表每次启动必然造成文件损坏，Import 后续仍有运行检查。

建议：详情复用现有全局锁；后端在同一 activity gate 下独立检查活动任务，明确启动和存档写入等操作的互斥规则，避免仅修按钮。保持正常启动、快速请求无闪烁和 MTool 子进程跟踪。

必要回归：同一活动任务下列表、卡片、详情入口均拒绝；后端拒绝应发生在 spawn 前；任务完成后恢复可用。

### CR-03 · P2 · 保存资料会重新产生自动名称别名

位置：`src-tauri/src/db.rs:1060`。

`commit_version` 已停止追加旧名称，但 `edit_game` 在保存任何资料时会将 `canonical_title` 拼入用户传入的 aliases，并将全部条目重新插入为 `manual`。更新后的名称会在一次普通资料保存后成为别名，后续更新再保留；因此更新、保存资料交替进行时仍可积累版本名称。

隔离复现：使用当前 `write_import_identity` 将临时游戏身份从 `Game v1` 切换为 `Game v2`。此时没有 `Game v2` 别名；仅修改游玩状态并保存，返回的别名即增加 `Game v2`。再次传入空别名数组保存，仍返回 `Game v2`。

建议：保存用户实际提供的别名，不自动补入标准名称；保留已有有效和手动别名。不主动清理旧历史名称，也不要把推断出来的自动条目伪装为用户添加。

必要回归：更新 → 仅改状态保存 → 再更新，不新增版本名称别名；手动别名保留；用户删除的别名不自动恢复；Journal 重放不重复插入。

### CR-04 · P2 · 失效的公共 MTool 路径阻断普通游戏导入

位置：`src-tauri/src/importer.rs:669`。

生成导入计划时，无论 `selection.mtool` 是否为 false，只要 settings 中有 MTool root，都会执行 `dunce::canonicalize(...)?`。此前有效的工具目录被移动、移除或所在盘离线后，普通直接启动游戏的导入也会整体失败，返回系统路径错误。

隔离复现：游戏库和新游戏来源均正常，选用 `Start.exe` 直接启动、`mtool=false`、没有随包清理，唯一异常是公共 MTool 路径不存在。`ImportStore::prepare` 返回 `os error 2`，没有生成可确认的普通导入计划。

建议：将“不存在路径的边界保护”与“MTool 启动依赖验证”分开。仍需保护工具路径及可解析的祖先，不能简单跳过所有保护；仅使用 MTool 的项目要求依赖完整，普通项目可独立导入。混合批次应按项目明确报告。

必要回归：工具目录失效时非 MTool 导入正常；MTool 项明确阻断；来源仍不能侵入公共工具范围；无关文件不被修改。

## 建议路线

### 第一阶段：修复上述四项，保持当前功能范围

先补删除身份保护，再统一启动任务锁，之后修复别名回填和失效工具路径。每项加最小必要回归，完成完整测试、检查及一次 Windows Release 构建。文件保护修复验收通过前不推进正式分发。

### 第二阶段：完成已经实现的里程碑验收

1. Import：同盘移动、跨盘复制、目标冲突、部分失败继续 / 撤回、重启恢复；确认新导入、待确认、导入记录之间的流转。
2. 更新与回退：RPG Maker、Ren'Py 各使用明确授权的样本完成保留存档更新、启动读档、回退后再次读档。
3. v0.4 / v0.5 / v0.6：随包 MTool 整目录回收与失败重试；查重明确选择保留 / 删除和状态重启保留；AppData 一次确认、取消、清理失败及本地存档不受影响。
4. 存档编辑：MV / MZ 真实槽位，Ren'Py 普通存档、签名与 persistent 重启；记录具体游戏、格式和结果。
5. 维护：同父目录改名、整库迁移、跳过项、公共 MTool / 本地 QSP，以及历史回退的限制提示。
6. 分发：干净 Windows 上单 EXE 首次启动、WebView2、可写位置和移动 EXE + data 后资料保留。Portable 专项验收保留为环境 / 路径机制变化时执行的专项检查，不增加到每次日常构建。

真实存档写回需要单独授权；继续遵守不备份或导出正式数据库的开发规则。

### 第三阶段：整理版本与正式分发

v0.4、v0.5、v0.6 目前是功能里程碑，配置仍为 0.3.1。验收完成后再决定发布版本，统一三处版本配置、CHANGELOG、README 和 Roadmap；发布提交应有成功 CI 和对应构建产物。当前 PR 完整检查并产出 EXE、main 完整检查并构建、正式 Release 完整检查和资产校验的策略可以保留。

### 再之后：以真实样本决定增量开发

- 完善 Unity 及其他引擎的明确存档路径识别；Unity 存档编辑按具体格式单独评估。
- 根据人工关联的真实漏配样本补名称和辅助身份规则，继续保留续作、DLC 和歧义保护。

- 暂不安排云同步、自动下载更新、任意存档对象编辑或大规模 GUI / App 结构重构。
