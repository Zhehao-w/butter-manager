# 2026-10-21 全量审查处理决定

审查基线：main `e17a5d69e387cf055caf65f7cea2b7da05ef092e`，应用版本 **1.3.3**，schema **13**。按用户确认处理三项 P2，并补充游戏库筛选修复；功能修复 PR #17 已合并，纳入 1.3.4；功能 PR 未改版本号，发布准备另行统一版本，数据库结构不变。

## 第 1 项：执行导入前复核来源归属，修复

待执行预览期间允许正常登记和关联目录。原实现只在生成预览时检查来源归属，旧预览可能搬走后来已关联到已有 UUID 的来源目录。

现在在整批文件操作及跨盘清单写入前，对所有 pending 项按最新库记录重新检查来源与安装目录的相同、父级及子级重叠；发生冲突即停止，提示重新生成计划并使用扫描入库或目录关联。此检查同时适用于新导入及版本更新的待执行来源，不改变已开始任务的恢复、撤回或提交后清理流程。

隔离回归覆盖预览后重新关联目录，以及新增父级 / 子级登记导致整批停止，核对来源存档内容、原 UUID 及库记录数量，确认未移动先前无冲突的批次项目。

## 第 2 项：其他游戏存档位于导入来源内，已接受

普通 Import 检查来源与其他游戏安装目录的重叠，但不另外枚举其他游戏的关联存档路径。若其他游戏的存档被人为放入待导入游戏目录，仍可能随来源目录搬移。

用户明确每个游戏的存档应只位于自身目录、AppData 或 Documents，不应位于其他游戏目录。因此接受这一现有边界，不安排跨游戏存档检查，后续审查不重复列为 issue。此决定不新增路径限制，也不改变安装目录归属、存档迁移、目录身份、Journal 或其他已有保护；它与先前接受的 MTool 清理边界分别记录。

## 第 3 项：完整扫描补空存档使用保存配置，修复

扫描默认候选的工作目录或引擎可能与已保存配置不同。原同步入口先过滤候选空存档，再使用候选的工作目录及引擎，因而遗漏实际可检测的存档。

现在对 ready 且目录仍对应原记录的已登记游戏，仅在已保存存档路径为空时重新检测，不依赖候选是否发现存档。检测使用数据库中实际生效的引擎、启动文件及工作目录，并包含本次同步允许刷新的自动启动默认值。保持手动完整扫描，不增加启动时扫描，不覆盖已有存档路径。

## 补充：游戏库「全部」与「需处理」筛选一致

「需处理」生效时，「全部」取消高亮；点击「全部」清除该状态和原有分类筛选。延续现有搜索及排序语义，复用原有控件，不增加界面布局。

验证结果见 [验证记录](validation.md)。所有回归使用隔离临时数据库、目录及合成文件，不访问或备份正式游戏、存档、数据库、WAL、SHM 或 `data/`；Windows 原生与实机验收独立完成。
