# 导入关联匹配改进计划

状态：2026-10-09，三个阶段已实施。名称、候选排序、小配置身份读取与确认后的别名保存已接入；保留既有准确匹配及人工确认流程。

## 实施与核对结果

- 一批导入复用一个名称倒排索引与身份缓存，最多显示五个候选。新的宽松比较均需确认；多个准确候选或前两名分差不足时取消自动关联。日文原名冲突、续作/章节/外传/重制差异保留阻断，DLC 差异保留提示。
- 基于回归夹具采用推荐门槛 68、歧义分差 8；这是匹配分，不能解释成概率，更多真实案例仍应继续验证。标题的多种算法取最佳值，特色 EXE、外部存档目录、静态项目身份只作辅助。
- 成功的版本提交事务同时保存来源原始标题为 `confirmed_import` 别名；不改手工显示名，不删除已有别名，不在预览/取消/失败时添加。重复提交不重复插入，回退保留已确认的标题关系。
- 使用正式库只读连接与源目录浅层分析，六例均唯一推荐到正确游戏：妹系罗盘、鸣人的假期、My Best Deal、ReSister、阿克梅西亚、公主协同效应。没有执行导入或更新，没有修改正式记录或真实存档。
- 正式库 573 条记录，本次 Debug 诊断预处理约 132ms；六例单次推荐约 0.5–16.7ms，不含目录分析时间。合成 500 / 2000 条库记录预处理约 45 / 186ms，随后各 100 次查询约 13 / 12ms；缺失配置缓存后不重复读取。以上是本机观测，不保证所有磁盘上的耗时。
- 前端四例确认流程、历史匹配、元数据/通用字段保护、歧义、取消、只读配置上限与链接拒绝、别名失败/重启/回退均有回归覆盖。只读诊断工具：`src-tauri/examples/import_match_preview.rs`。
- 最终验证通过：Rust 181 项通过、1 项既有测试忽略，React 138 项通过；格式检查、Clippy（所有目标、警告视为错误）、前端构建及 Windows Release 构建均通过。

## 当前问题

当前 `import_matching::Name` 用名称规则返回固定分数，`importer::matches` 仅比较标准名、显示名、别名和安装目录名。分数不是经过校准的匹配概率。中文、日文标题和包装描述仍容易拼成一个字符串；英文名称规则要求词集合一致，且部分规则要求至少两个词、总长至少 12。

本轮四例（依据用户截图、实际源目录名及当前代码）：

| 游戏 | 漏匹配原因 | 计划使用的证据 |
| --- | --- | --- |
| 妹系罗盘 / 姊妹指南针 | 中文译名不同；共同的日文主标题 `シスターズコンパス` 后，新版有完整副标题，旧版只有主标题并附 AI 汉化描述 | 日文主标题一致，副标题缺失降权，结合游戏身份或特色启动文件；仅推荐确认 |
| 鸣人的假期 | 五字中文标题相同，但新版的 `内部赞助付费完结版` 没被当作包装描述 | 完整中文主标题相同，包装描述单独记录；必要时比较 Ren’Py 身份 |
| My Best Deal | 旧版残留 `pc` 单词；去掉后英文三词总长 10，仍达不到现有部分规则的 12 字符门槛 | 三词完整标题一致；版本和平台分开；可比较特色 EXE 或 Ren’Py 身份 |
| ReSister | 单词英文名不满足多词规则；中文译名增加「两人」，新版还有 DLC 标记 | 特色英文名一致，中文高度相似、特色 EXE / 存档身份辅助；DLC 作为差异保留，明确确认 |

## 研究结论

采用记录关联的思路：候选召回、多项证据评分、冲突处理、用户确认。参考 [Splink 的多字段匹配模型](https://moj-analytical-services.github.io/splink/topic_guides/theory/fellegi_sunter.html)、[候选分组](https://moj-analytical-services.github.io/splink/topic_guides/blocking/blocking_rules.html)与[词频调整](https://moj-analytical-services.github.io/splink/topic_guides/comparisons/term-frequency.html)。借鉴方法，在现有 Rust 中实现轻量方案；不引入 Splink/Python 或训练框架。

[RapidFuzz 官方示例](https://github.com/rapidfuzz/RapidFuzz#token-set-ratio)说明：词集合比较中，一串是另一串的子集时也能得到 100 分。因此模糊相似度只用于候选排序，不能单独授予自动关联。官方 [Rust 实现](https://docs.rs/rapidfuzz/latest/rapidfuzz/)可作为编辑距离工具的备选；第一阶段优先使用现有依赖与小规模字符二元组比较，不安装新依赖。

## 分阶段实现

### 第一阶段：统一名称表示与推荐排序

1. 保留原始名称。生成多个标题表示：完整名称、中文标题片段、日文主标题和副标题、英文词组、已确认别名。Unicode NFKC、大小写与空格/下划线/常见分隔符统一处理。
2. 版本、平台和汉化包装信息独立记录。版本变化不能妨碍同游戏推荐；续作数字、章节、外传、重制和 DLC 不能当成普通噪声删掉。包装信息集中处理，避免继续在 `compare()` 叠加个案分支；未知描述保留。
3. 英文比较完整词组与有区分度的单词；中文和日文用 Unicode 字符二元组覆盖率、编辑相似度。主标题一致而副标题缺失可以召回，双方明确不同的副标题需降权或排除。不能用任意短子串包含就推荐。
4. 一批导入只预处理库内名称一次。先按别名、特色词组、字符片段召回候选，再精排；不把相同引擎作为必需条件，允许未知或手工引擎。
5. 同一个字段的多种算法取最佳证据，避免标题、目录名、别名的同源信息反复加分。常见词（Game、Princess 等）降权，罕见标题词权重更高，罕见性加分需封顶。
6. 展示最多 3–5 个有效候选和可读理由。新加入的模糊结果一律需要用户确认；既有准确匹配保留原行为，但多个强候选必须解除自动选择。最高分不明显领先第二名时列为歧义。分数叫匹配分，不声称是概率。

第一阶段目标：四例正确游戏均进入推荐候选；不会自动执行更新或修改真实游戏记录。

### 第二阶段：对歧义候选补充游戏身份

优先复用已扫描字段，必要时对前几名候选按需读取小配置，缓存到当前分析会话，不新增数据库表：

- Ren’Py：静态 `config.save_directory`、项目/发行名称。现有 `save_detection.rs` 已能读取部分静态配置；[Ren’Py 官方文档](https://www.renpy.org/doc/html/config.html#var-config.save_directory)说明存档目录配置的含义。名字可因发行方式变化，不作为绝对唯一 ID；不执行脚本、不解包存档或运行游戏。
- Unity：现有 `app.info` 中的 company/product；其他引擎复用可用的项目名。通用模板值不加分。
- 特色 EXE 名称可辅助；`Game.exe`、`nw.exe` 等通用名称不提供同游戏证据。Ren’Py 的 32/64 位发行 EXE 可做已知平台后缀归一化，但保留实际启动路径。
- `<GAME>/save`、`www/save`、`game/saves` 等通用存档路径没有身份价值；真正带游戏标识的外部目录可辅助，不能单凭共享路径决定关联。

使用有上限、只读、可取消的现有文件读取机制。库目录离线或文件缺失时继续提供名称候选，不强制深度扫描，不全盘读取 EXE、不计算整份游戏哈希。

### 第三阶段：复用用户已经确认的关系

建议在用户明确确认关联且更新成功后，将标题变体记录到已有 aliases；清理版本和平台信息需谨慎，保留原始标题供解释。点击临时候选或取消计划不写入别名。

这一阶段另行落实确认后的保存时机及失败处理；保留用户手工名称、原有更新/回退行为。未来同类译名可以直接利用已确认别名，不必扩大全局模糊规则。

## 验收范围

- 将本轮四例、前两轮「阿克梅西亚」「公主协同效应」制成合成名称与元数据夹具，全部正确候选进入前几名，新增模糊候选不会自动关联。
- 保留现有别名与准确匹配、续作/章节冲突测试。追加同系列不同副标题、短通用名称、类似英文名、DLC 及独立扩展版本、同引擎且使用 Game.exe 的无关游戏、多个候选接近的反例。
- 列表搜索、用户取消、手工关联覆盖、文件缺失以及用户引擎字段保持不变。
- 离线比较新旧实现的正确候选覆盖率、候选误报、首位排序和歧义数量；仅使用合成夹具或只读核对，不修改正式数据库。
- 用 500 / 2,000 条合成库记录与批量导入测量耗时、文件读取量，保证界面可取消且不新增默认完整扫描。评分门槛与前两名分差以这些结果校准，不先拍定一个百分比阈值。
- 运行相关 Rust/React 回归、格式、Clippy、前端和 Windows Release 构建；此前单独的 UI 文案改动未运行测试，本次匹配实施按用户要求测试。

## 范围

匹配实现主要位于 `import_matching.rs`、`import_recommendations.rs` 和 `importer::MatchIndex`，保留现有 `Match` / 确认流程。身份读取复用 `save_detection.rs` 的安全小文件读取。仅在现有版本提交事务增加别名，不改变文件移动、回退或日志格式。不修改 Portable 目录、schema 或 Codec，不引入新依赖。
