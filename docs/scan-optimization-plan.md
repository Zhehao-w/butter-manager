# 大型游戏库扫描优化计划（v0.1 历史）

本文保留首次扫描优化的需求和实施依据；当前操作与界面见 [README](../README.md)，后续规划见 [roadmap](roadmap.md)。下方原问题描述不代表当前仍有这些问题。

日期：2026-10-05。状态：用户已授权执行，v0.1.1 首轮实现完成；以下保留原始问题分析和方案。

## v0.1.1 实现状态

已实现后台任务、协作取消 / 跳过、快速两层扫描、1 / 2 / 4 worker、会话快照、登记复用 / 回滚、简化预览和显式深度分析。

实际边界：发现最多 5,000 个游戏 / 20,000 个 root 条目；快速分析每游戏最多 2,000 项、根目录及一层子目录、5 秒软预算；主动深度分析最多 20,000 项 / 四层 / 30 秒软预算。每目录最多排队 64 个子目录，最多保留 32 个 EXE、8 个 BAT；BAT 最多 256 KiB，单行最多 4 KiB。每条响应最多 100 个候选，前端约每 400 ms 读取进度；变更日志超过 20,000 条会合并为最新快照，落后游标仍能分批恢复。

默认全库快速扫描只用文件名、必要 EXE 文件信息与固定引擎标记，不打开 PE / BAT。架构与 BAT recipe 由主动“分析 EXE / BAT”或深度分析补充；这两种分析均使用后台任务、进度和取消。

已增加处理较久提示；保存逐候选项数与耗时，注册 EXE 使用大小 / 修改时间做轻量变更检查。原生文件覆盖可明确重新确认已变化 EXE，路径边界验证始终执行。深度分析取消会保留此前快照。

跨重启缓存、8 worker、细分每类 I/O 计数 / CPU / 内存 / 最慢目录诊断、用户可配置的全库预算留待后续。本轮采用有界目录数组与固定 worker，不增加无界线程或资源预读。真实测量和夹具结果见 [validation.md](validation.md)。

## 问题与已确认事实

用户的游戏目录约 1.3 TB，当前扫描长时间显示“正在处理”，缺少取消与跳过入口。

代码检查确认：

- `scanner::walk` 对每个游戏递归扫描四层，对每个目录项执行文件信息查询；每个游戏最多检查 20,000 项，并非全库总上限。
- 默认会进入不少不含启动文件的资源目录。虽然不读取图片、音频、视频正文，遍历与文件信息查询仍有成本。
- `engine` 单独遍历游戏根目录，未共用扫描发现的信息，也未应用同一预算。
- `scan_root` 串行分析所有游戏，完成后一次性返回；没有分批结果、进度、耗时统计和取消信号。
- UI 使用一个全局 `busy` 状态，把扫描、资料保存和启动等操作混在一起，扫描时多个操作入口被禁用。
- `register_games` 在加入数据库前重新完整分析所选目录，重复了预览阶段的扫描。

尚未采集真实库的逐目录耗时、项数与磁盘类型。不能仅凭容量确认当前任务卡在哪里，也不能承诺固定的全库完成时间。需求收集时不重新遍历 1.3 TB 游戏库做诊断；实现后进行了有时间限制的只读测量。

## 目标与范围

默认操作应先显示目录列表，逐步补充启动信息；能看到当前处理位置和耗时，能取消整个扫描或跳过当前游戏；保留已完成的结果供用户确认。扫描不移动、删除或修改游戏及存档，不依赖 Windows Search。

此项属于 v0.1 可用性修正，优先于 v0.2 Import / Matching。目录选择器与设置弹窗已在同一轮实现。

首次录入的信息简化、登记进度、简单版本提取和详情 / Play 交互见 [v0.1-usability-plan.md](v0.1-usability-plan.md)。其中“登记复用与进度”提升为第一轮必要修正，不等待持久化缓存。

## 已补充的目录结构与预览需求

用户确认当前库的 EXE 最多位于以下两个位置（以 `Butter` 为 Game Root）：

```text
Butter/gamexyz/任意名称.exe
Butter/gamexyz/gameabc/任意名称.exe
```

从 Game Root 算，EXE 在第一或第二层游戏目录；从每个直属游戏目录算，只需检查根目录及其一层子目录。默认不再做四层递归，Unreal 等更深的定向路径归入显式深度分析。本阶段不假设 EXE 叫 Game.exe。

当前 UI 的“关闭预览”直接清空 `scan`，未登记结果只能通过重新扫描获得。这需要修正为：

- **关闭 / 收起预览**只隐藏面板，保留扫描快照、已选项目、筛选和任务状态；独立维护面板是否显示，不把结果清空。
- 主页面提供“查看上次扫描结果”入口，显示结果数量、时间和完整 / 部分状态。重新打开不访问游戏磁盘，也不重新扫描。
- 隐藏面板、取消扫描、重新扫描、清除结果是不同操作。隐藏面板不取消正在运行的扫描；主页面仍保留进度与取消入口。
- 取消后保留已完整分析的候选，可重新打开预览；重新打开预览不等于继续被取消的任务。继续剩余扫描若以后加入，应是明确的独立操作。
- 已选项目登记成功后，快照中更新“已登记”状态，未选候选保留；不因为登记一部分游戏就清掉整个预览。
- 第一轮至少保证当前应用会话内可恢复预览。跨重启恢复属于持久化快照，沿用后续缓存安排；届时恢复的内容需标明时间，并在登记前验证相关路径，不能把旧结果当作最新扫描。
- 保存无关设置，例如 MTool Root，不应清除预览。Game Root 改变时旧结果标记为其他 root 的历史快照，不能直接向新 root 登记；需要明确提示。

两层目录还要求区分外层登记目录与实际游戏启动目录：相对 EXE 可以保存为 `gameabc/任意名称.exe`，包装目录中的实际游戏通常需要以 `gameabc` 为工作目录。扫描应识别并记录启动工作目录，允许纠正，不能一律沿用外层目录。子目录 BAT 的 `%~dp0` 是 BAT 所在目录，recipe 转换时要正确重定位到登记目录下，并继续执行路径边界验证。

## 实施顺序

### 1. P0：可取消、可观察的扫描任务

- 引入独立扫描任务状态：`scan_id`、规范化 root、扫描方式、状态、取消标志、当前游戏 / 子目录、已完成数、发现数、处理项数、警告数、耗时和已完成结果。
- 生命周期：`running → cancel_requested → cancelled`，以及 `completed` / `failed`。终态只发布一次；取消和自然完成的竞争需要有一致结果。
- API 方向：开始扫描并立即返回 ID；读取任务快照；取消指定任务；跳过当前游戏。任务状态独立于数据库锁，取消命令不能排在扫描完成之后。
- 使用共享取消标志，在目录枚举、迭代、递归、文件信息查询、PE / BAT 读取前后检查。仅取消前端等待或丢弃 Future 不算取消扫描。
- 进度和完成候选通过 Tauri 通道或事件分批传递；每个消息携带任务 ID / 序号。先建立接收通道再开始任务，快照接口用于恢复或补全丢失事件。
- 通常每 150–250 ms 合并发布一次进度，候选分批展示；限制消息、警告和快照占用，避免大量 IPC / React 更新形成新的瓶颈。
- 同一库同时只允许一个扫描任务。取消请求发出后，直到 worker 真正结束前仍占用任务槽；新任务不接受旧任务的延迟结果。
- 不持有数据库锁进行磁盘遍历；启动前取出已登记路径映射，避免每个结果单独查询数据库。

取消采用协作方式。已开始的同步文件系统调用可能要返回后才能响应；UI 先立即显示“正在取消”，不能伪装成已经停止。`spawn_blocking` 的运行中任务不能靠 `abort()` 强行停止，参考 [Tokio 官方说明](https://docs.rs/tokio/latest/tokio/task/fn.spawn_blocking.html)。

“跳过当前目录”指跳过当前游戏目录的剩余分析，继续下一个游戏。该结果标为未完整分析，可后续单独重试。取消整个任务则停止继续调度，已完整分析的候选保留为预览，不自动登记。关闭应用时请求取消；不会为停止扫描而终止游戏进程。

### 2. P1：默认快速扫描，深度分析按需进行

默认扫描分两步：

1. **发现目录**：只枚举 Game Root 的直属游戏目录，尽早分批展示目录名及是否已登记。初始总数未知时显示发现数，不显示虚假百分比。
2. **轻量分析**：每个游戏检查根目录 EXE、BAT 和少量明确的引擎标记，并在需要时检查一层候选包装子目录中的启动文件 / BAT。默认范围对应用户的两种目录结构；更深的 Unreal `Binaries/Win64` / `Win32` 等路径只在显式深度分析中做定向搜索。

进一步规则：

- 默认不递归进入 Unity `_Data`、RPG Maker 图片 / 音频资源、node_modules、Tool、存档等内容目录。不对所有不熟悉的子目录自动做四层搜索。
- 复用同一次根目录枚举发现的 EXE、目录名、`.pck` 等线索，减少 `engine` 与 `walk` 重复工作；Windows 链接 / junction 安全检查仍保留。
- 根目录 EXE 先展示，PE 架构和 BAT 解析作为后续轻量补充；不为识别游戏读取资源正文、计算整库大小或做内容 hash。
- 包装子目录内的引擎标记在对应实际游戏根目录检查；BAT recipe 保留它的原始目录上下文。一个外层目录发现多个不同游戏 / 多个 EXE 时标记歧义，不擅自拆分或合并 identity。
- 后端保留多个 EXE 候选，首次录入默认只展示一个建议 EXE；替代候选在用户点击人工 override 时展开。未知引擎或找不到 EXE 的目录保留在列表，不直接丢弃。
- 增加“深度分析此游戏”和“选择 EXE”入口；深度扫描仅由用户显式请求，仍支持取消和预算。不在普通全库扫描中自动升级为深度扫描。
- 首次录入不逐项展示“未深入扫描”路径或正常跳过资源的提示；技术诊断按需展开。没有建议 EXE 时简短提示手选，或由用户主动请求单独深度分析。

减少无用遍历与多线程配合实施。用户提出考虑用更多资源换取速度，将可选并发扫描模式纳入计划；最终默认档位根据实际磁盘测量决定。

### 可选性能模式：有上限的多线程

- 以一个游戏目录为工作单元，使用固定数量的 Rust worker，并行分析多个游戏。全库仍是一个扫描任务，不为每个文件单独创建线程。
- 初步提供“低占用 / 均衡 / 性能”三个档位，对应 1 / 2 / 4 个目录 worker；高级选项可试验 8 个。数值属于待验证的计划参数，不承诺线程数翻倍就速度翻倍。
- 把目录枚举、metadata 与文件打开视为磁盘工作；PE / BAT 解析使用有限的处理并发。即使 CPU 核数多，也不按核数无限增加同一块磁盘的访问。
- SSD 可先对比 2 / 4 个 worker；机械盘先对比 1 / 2 个，关注随机寻道与磁盘响应。现阶段未确认用户磁盘类型，不直接开启最高并发。
- 使用有界任务队列，限制同时打开的文件数、结果消息与缓存内存；不为了利用内存而预读游戏资源正文。SQLite 登记仍通过独立的串行事务处理。
- 取消信号覆盖全部 worker，并停止继续取任务；等待已开始的系统调用返回。只有所有 worker 停止后才进入 cancelled 终态。
- 并发时显示正在分析的游戏列表，允许逐项“跳过此游戏”。跳过请求携带候选 ID，不依赖一个容易变化的全局“当前目录”。“取消扫描”停止整项任务。
- 已完成结果可先展示，最终排序稳定。进度按目录状态汇总，不能因并发完成顺序造成重复计数或候选覆盖。
- 性能档位只增加相同扫描范围的并发，不自动扩大扫描深度或遍历资源目录；深度分析仍是独立的显式操作。

### 3. P1：预算与慢目录提示

- 统一所有分析路径的项数、深度和文件读取预算，包含引擎识别；快速扫描预算小于原来的每游戏 20,000 项。具体值通过夹具和实际库测量确定。
- 使用每个游戏的软耗时预算：在检查点发现超限后标为“未完整分析”，继续其他游戏；它不是能够强制中断单次系统 I/O 的硬超时。
- 当前目录长时间没有新进度时显示耗时及“可能等待磁盘响应”，提供取消 / 跳过入口。
- 记录每个游戏的目录枚举、metadata 查询、EXE / BAT 读取次数及耗时，并汇总最慢目录。诊断只记录必要元数据，不抓取文件正文。
- 可设置全库项数 / 时长预算；达到预算时保留结果，明确标示剩余未扫描部分，不能报告“全部完成”。

### 4. P1：登记复用与进度；持久化缓存后续安排

- 登记使用 Rust 后端保存的扫描预览快照 / 已选候选 ID，而不是相信前端提交的任意扫描元数据。
- 加入游戏库前只重新验证 root 归属、目录存在、链接边界以及拟保存的 EXE；EXE / BAT 若发生变化，仅重验相关文件或要求重新分析。不再完整递归扫描一次。
- 登记作为独立后台任务，显示准备 / 验证 / 写入 / 更新列表的阶段及数量；保存人工 EXE override 与用户确认的版本。登记事务中可取消并回滚未提交内容，成功 commit 则如实报告已加入。
- 复用 SQL prepared statements 与事务批量写入，优化关联查询与列表更新；取消或失败后保留预览与勾选。具体性能瓶颈通过分阶段测量确认。
- 保持同一路径重复登记幂等；预览过期、Game Root 改变或任务数据已清理时给出明确提示。
- 第一轮先做本次会话内的结果复用。持久化轻量缓存后续再做，缓存键包含扫描规则版本、规范化路径和相关 EXE / BAT 的大小 / 修改时间。
- 缓存展示上次分析时间，允许手动刷新。不能单凭游戏根目录 mtime 声称整个目录未变化，因为嵌套文件变化不一定反映在根目录时间上。
- 不引入全盘 watcher、USN journal、Windows Search 或资源文件 hash。

## UI 交互

- 替换通用“正在处理…”为独立扫描区域：阶段、正在分析的游戏 / 路径、已完成 / 已发现、耗时、警告，以及始终可点击的“取消扫描”和逐游戏的“跳过”入口；扫描前可选择性能档位。
- 已发现目录与已完成分析的结果持续可见，状态简短呈现；首次录入只突出建议 EXE / 人工 override 和建议版本，逐资源 / 未深入路径诊断默认隐藏。
- 扫描中仍可搜索、浏览已登记游戏和打开详情。避免全局禁用整个界面；开始第二次扫描和改变 Game Root 在现有任务结束前受限。
- 扫描期间暂不登记正在变化的预览；完成 / 取消后可选择完整候选登记。未完整候选先补充分析或手工指定 EXE，再明确确认。
- 快照恢复和终态事件即使出现重复，也不重复加入候选或覆盖后续任务。
- 大量结果分批渲染，并分页或限制一次渲染条数。不要把全库所有警告和 BAT 详情一次展开到页面。

## 验证与验收

- **取消**：夹具中途请求取消后，不再开始下一个文件操作或游戏；保留完整结果。UI 点击反馈目标不超过 250 ms，正常本地 I/O 下 worker 停止目标不超过 1 秒；磁盘阻塞场景不承诺硬停止时限。
- **跳过与竞争**：跳过慢游戏可继续下一项；取消与完成竞争、重复取消、旧事件晚到、任务失败、关闭窗口都能得到一致终态。
- **性能结构**：构造很多资源文件的 Unity / RPG Maker 夹具，快速扫描不递归枚举资源树，成本不随着其资源文件数成比例增长；根目录本身的枚举成本仍必须如实计入。
- **正确性**：默认识别直属游戏根部 EXE 与一层包装子目录 EXE，任意中日文 / 空格名称和多个候选正常；包装目录的工作目录与子目录 BAT recipe 正确。更深 Unreal 定向路径通过显式深度分析识别。链接不越界，Unknown 不丢弃。
- **预览恢复**：收起再打开保持候选和勾选，不产生磁盘扫描；隐藏时仍可取消；取消的部分结果可恢复显示；登记部分项目不会丢失其他候选；无关设置变化不清空结果，改变 root 会标记旧快照归属。
- **登记**：登记已分析候选不会触发全目录重扫；预览后 EXE 被删除或替换、root 改变、候选过期时能检测并提示。
- **缓存**：只复用有效的轻量结果，手动刷新生效，嵌套路径变化不被根目录 mtime 掩盖。
- **资源占用**：单个扫描、分批 IPC、警告和结果保留有上限；大量目录夹具中 UI 不积累无限消息。
- **并发**：分别测量 1 / 2 / 4 个 worker 的总耗时、首批结果时间、CPU / 内存及磁盘响应；验证同时取消全部 worker、逐游戏跳过、乱序完成与稳定汇总。8 个 worker 仅在测量有收益且取消能力正常后作为高级选项开放。
- **真实库**：用户允许开始实现后，先在小范围验证，再对真实库执行一次可取消扫描，记录首批结果时间、总耗时和最慢目录。基于测量决定具体预算与并发，不在计划阶段声称已有速度提升。

实施顺序为 P0 → 快速扫描与预算 / 简化录入 → 登记复用与进度 → 有界并发及性能测量。持久化缓存视第一轮结果决定；始终停留在 v0.1，不加入 Import / Update / Delete。
