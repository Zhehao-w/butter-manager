# v0.1 首次录入与交互改进计划（历史）

以下是 v0.1 的需求与实施依据，文中的功能范围、旧交互问题和待改流程仅对应当时版本。当前导入更新、删除与界面规则见 [README](../README.md) 和 [v0.3 实施说明](v0.3-implementation.md)。

日期：2026-10-05。状态：用户已授权执行，v0.1.1 实现完成。

建议 EXE / 手工选择、版本识别及人工覆盖、批量登记快照复用与事务回滚、设置与详情弹窗、局部 Play 状态已实现。下面保留需求和设计依据。自动化 DOM 测试覆盖预览恢复、覆盖值提交、原生选择器调用、未保存关闭确认、旧任务晚到、取消与 Play 挂载 / 重开状态；真实视觉和第三方窗口行为仍待实机验证，详见 [validation.md](validation.md)。

本计划补充 [扫描优化计划](scan-optimization-plan.md)，处理用户实际使用中提出的五项问题。范围仍为 v0.1 游戏库与启动器，不加入更新、删除或游戏文件搬移。

## 1. 首次录入只突出建议 EXE 与人工 override

用户不需要首次录入时看到大量“未深入扫描：E:\Butter\...”信息。默认流程应尽可能简单。

- 每个候选只突出游戏名称、建议启动 EXE、可编辑的版本，以及是否选中加入库。技术信息不占据主流程。
- 默认仅展示一个建议启动 EXE，但 Rust 后端仍保留候选列表；用户点击“更改启动程序 / 手工选择”后才展开替代候选或使用原生文件选择器。
- 手工选择的优先级高于扫描建议，重新打开预览或补充分析时不能覆盖用户选择；登记必须使用 override 后的 EXE，同时正确保存包装目录的启动工作目录。
- EXE 仍需位于该登记游戏目录内，支持 Unicode、空格和任意 EXE 名。选择器和后端都应验证文件及路径归属。
- “未深入扫描”、普通资源跳过、PE 架构、engine heuristics、逐文件路径和 BAT recipe 默认隐藏。它们仍可记录到后端诊断或按需展开的分析详情，隐藏展示不等于后台继续深扫。
- 找不到 EXE 时只显示“请选择启动程序”，用户可先留待配置。多个合理候选可提示“可更改启动程序”，不把所有技术警告展开。
- 真正阻止登记 / 启动的问题仍用简短的人话提示，例如“目录不可访问”或“选择的文件已不存在”；这与正常的浅层扫描提示分开。
- MTool target / loader 和原 BAT 的分析详情仍可在用户主动配置 MTool 时查看。界面不会因隐藏 BAT 信息而执行未经确认的 recipe。

## 2. 优化第一次批量加入库，并显示真实进度

当前 `register_games` 对所选目录重新调用 `analyze_directory`；数据库返回全库时也逐项读取游戏、别名和存档位置，前端收到结果后一次渲染。重复遍历已确认存在，具体各阶段占比仍需测量。

计划将登记任务分为：准备候选 → 验证所选目录 / EXE → 写入数据库 → 更新列表。

- 直接复用 Rust 保存的扫描快照和人工 override，不再完整扫描所选目录。只对必要路径、存在性、文件变化与权限做轻量验证。
- 登记进度显示阶段、当前游戏、已验证 / 总数、已处理数量、耗时和失败项目。明确区分“验证完成”与“数据库已提交”，不能提前声称已加入。
- 独立于扫描状态建立登记任务状态；较长的验证放在后台，不占用 UI 线程或长时间持有数据库锁。
- 复用 SQL prepared statements，在事务内批量写入 games / aliases / save_paths；保持安装路径唯一约束与重复登记幂等。SQLite 写入不靠大量线程并发。
- 第一轮保留所选批次的原子登记：验证阶段取消后不写库；事务中收到取消请求则在检查点回滚尚未提交的批次。已经完成提交时显示成功，不能把成功提交伪装成“已取消”。单次文件 I/O 或 commit 正在执行时不承诺立即中断。
- 数据库异常或取消回滚后，保留候选与勾选，支持检查错误后重试。错误验证不丢掉原预览。
- 优化全库读取的逐项查询，尽可能批量查询关联元数据；登记后返回本批新增 / 已存在状态，避免每加一批就从头加载并重绘整个库。
- UI 分批更新可见行，必要时分页；预览中已登记项目更新状态，其他候选保留。
- 测量验证、数据库写入 / commit、查询返回及 UI 更新各阶段耗时。只有测量支持时才进一步调整批次或处理并发。

这项登记复用与进度反馈列为第一轮扫描优化的必要组成，不留到“以后加缓存”才做。

## 3. 从名字提取简单版本号，复杂版本手工填写

- Rust 在已有目录名和所选启动 EXE 的文件名中识别明确的 `v1.2`、`v1.2.3`、`V1.2.3.4` 等简单数字版本 token；不为了读版本去遍历全部文件或打开游戏资源。
- 第一轮仅处理 `v` / `V` 加点分数字。没有明确 token、后缀复杂（例如 beta / rc）、多个不同版本或来源冲突时，交给用户输入。
- 版本仍是字符串：保留匹配 token 和原始数字格式（如 `v1.02.3`），不强制 SemVer，不猜大小，不自动触发覆盖或更新。
- 在录入预览中填入建议版本，用户可直接 override；无匹配时填 Unknown，手工编辑保留任意非空版本字符串。
- 来源记录为 `folder_name`、`file_name` 或 `manual`，可在需要时查看来源。用户明确填写的版本不能被重新扫描覆盖。
- 首次登记保存预览确认后的版本与来源，不再全部落为 Unknown。已有库的手工版本不因这项功能上线而被批量重写。
- 版本解析是独立的小函数，测试明确版本、前导零、中日文文件名、大小写、多个 token、复杂后缀、日期及无版本输入，避免把无关数字当版本。

## 4. 详情不再挤窄列表，也不依赖页面顶部

用户反馈：选择游戏时列表突然缩窄约一半；详情固定在主内容顶部，从列表底部选择游戏后要向上滚动才能查看。

代码中的 `main` 使用左右 flex 布局，detail 加入后占据约 520px；列表与详情没有共同固定视口，确实会造成这些问题。

- 拟采用独立的居中详情 popup / modal，打开时直接出现在当前视口，保持底层列表宽度、列宽、筛选和滚动位置。
- 如果后续选用侧边抽屉，也必须是覆盖层，不能把列表挤成一半。具体外观仍可随用户后续要求调整。
- 详情内部独立滚动，标题、关闭入口和主要动作易于找到；长存档配置 / 别名不能让 Play 或关闭按钮不可达。
- 关闭后回到原列表行与原滚动位置，恢复焦点；从列表顶部或底部打开的行为相同。
- 弹层显示 / 隐藏不因为浏览器滚动条变化而导致列表横向抖动，保持有效的键盘导航。
- 未保存的编辑不能因为误点遮罩、切换游戏或关闭而无提示丢失；关闭行为与设置弹窗的交互保持一致。

## 5. 修正点击 Play 的界面闪动

用户报告点击 Play 后应用界面闪一下。目前 Play 共用 `perform`：切换全局 busy，并在页面顶部短暂插入 / 移除“正在处理”条，还会清除消息。由此引起的布局位移是代码中确认存在的候选原因，尚未做视觉复现，不能断言已确定唯一原因。

- 将启动状态从全局 busy 分离，以所选游戏为单位显示“启动中”，防止重复点击，但不重排列表、扫描区域或详情。
- 在按钮或固定位置展示反馈，不在页面上方临时插入占高度的提示；错误在详情或稳定的通知区域显示。
- 启动后保持应用当前选中项、详情状态、列表宽度和滚动位置；不重载游戏列表，不重新挂载整个详情。
- 后续验证区分应用内容布局跳动、窗口焦点切换、系统控制台闪现与游戏自身窗口出现。若是 helper 控制台问题，仅针对确定的 console helper 处理窗口方式，不盲目隐藏游戏窗口。
- 保留 Direct 和已确认 MTool 启动语义；不为消除闪动而提前宣称启动成功、去掉错误报告，或改成执行下载 BAT。

## 验收与优先级

1. 首次录入默认没有逐资源 / 未深入路径警告刷屏，仅有一个建议 EXE 与可用的人工 override；override 会真正写入并用于启动。
2. 大批量首次登记复用扫描结果，不重复完整遍历；阶段和数量持续可见，可取消 / 回滚，异常后候选和勾选仍在。
3. 简单版本自动建议并正确持久化，复杂 / 冲突版本由用户填写，手工值不被后台覆盖。
4. 在列表底部打开任何游戏时，详情立即出现在视口；列表不缩窄，关闭后位置不变。
5. Play 的等待 / 结束不会改变应用布局、滚动位置或卸载详情；真实游戏窗口出现不误记为应用闪动。

先做扫描 / 登记任务与简化录入，再补简单版本、弹层详情和启动状态；实现后才运行相应测试、构建和手工验证。本轮实现与验证结果已记录；后续继续验证真实游戏与 MTool。
