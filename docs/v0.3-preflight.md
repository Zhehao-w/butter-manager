# v0.3 开发前的三项 blocker（历史，已处理）

以下为 2026-10-07 的前置补强记录，三项已处理，随后已开发 v0.3 更新和回退。当前新导入/更新只预检运行进程，不遍历全部资源检查占用；存档、独立删除、回退和旧格式记录保留各自保护规则。当前流程见 [v0.3 实施说明](v0.3-implementation.md)。

日期：2026-10-07。本轮只补强现有功能，不开放已有游戏更新、替换或版本回退。

## 自动化基线

banner 动画新增了包裹层，旧 App 测试仍断言 banner 的直接父元素。改为检查它位于独立的悬浮通知容器内，保留扫描不自动跳页、结果按钮导航的行为验证。

## 导入记录容错

`ImportStore::open` 逐条加载记录。截断 JSON、无效操作身份、未知状态、缺少或损坏的文件清单、目录跳转及重复清单路径会形成恢复问题，不让该条计划进入可执行集合，也不阻止管理器打开。限制记录与清单读取大小，拒绝链接记录。正常计划继续可查看。

隔离是逻辑隔离：原始 JSON、清单、游戏、来源和暂存目录全部原位保留，不改名、不覆盖、不删除。不尝试从损坏内容猜测文件归属。存在无法确认的记录时，阻止导入执行/撤回、删除、目录关联、相关设置更改及数据库清空；启动请求也不绕过未恢复的文件操作。

导入导航显示“需处理”，导入页提供持久提示、记录详情及“打开记录文件夹”。修复原记录后重新启动以重新验证。没有“忽略并继续文件操作”按钮。数据目录本身创建失败等系统权限错误仍会报错，不能把它当成一条损坏记录跳过。

## 游戏运行与文件占用

新增共享 `runtime` 模块：

- Direct EXE 和本地 QSP 保留实际进程句柄；默认应用在系统返回句柄时也跟踪。检查句柄存活状态而非游玩标签，不受 PID 重用影响。
- 文件操作前枚举实际进程映像路径，检查游戏/存档范围，可发现手工启动的本地游戏，以及管理器重启前已存在的游戏进程。
- MTool 注入启动的游戏通过游戏目录中的实际进程识别，公共 MTool 窗口不被当成每个游戏的运行状态。
- 独占只读探测确认存档和资源是否被其他程序占用。匹配游戏文件名但无权查询进程路径时，保守阻止操作。
- 删除预览和执行、目录关联、导入移动/发布/来源清理及撤回接入检查。不自动关闭用户游戏或播放器。

这是文件操作前的检查，不是持续锁住整个游戏目录：另一个程序仍可能在检查后启动或打开文件。现有移动流程保留目录身份、内容复查及失败保留机制；v0.3 的替换执行器仍须在各切换阶段复查并支持失败恢复。

默认应用可能复用现有进程而不返回句柄；这时只能依赖可识别的本地进程与文件占用检查，不能保证识别所有外部播放器或浏览器会话。第三方播放器、外部启动器及引擎兼容性需要真实样本验证。

Windows API 依据：[进程快照](https://learn.microsoft.com/en-us/windows/win32/api/tlhelp32/nf-tlhelp32-createtoolhelp32snapshot)、[ShellExecute 的进程句柄选项](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/ns-shellapi-shellexecuteinfow)。

## 验证范围

新增独立临时夹具覆盖损坏记录与缺失清单、非法清单、重新读取修复记录、锁定存档阻止任何回收、锁定来源阻止导入且关闭后可重试。原生进程测试使用复制到临时目录的系统命令解释器，隐藏运行并通过关闭测试输入结束，只操作测试自己的进程。

正式数据库 schema 不变，没有创建数据库、WAL、SHM 副本或记录导出；没有对真实游戏执行移动、删除或启动。无 GUI 自动化。
